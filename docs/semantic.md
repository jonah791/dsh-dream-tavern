## 1. 定位与反定位

### 1.1 定位（是什么）
运行在 DSH 上的**文字游戏 / 角色扮演创作与游玩宿主**，两个并列目的：

1. **娱乐**：导入或制作人物卡，自由游玩或沿剧本推进。→ **2026-09-22 主人定调：该目的归 `dsh-profile-tavern`**（他那边满足游玩需求），本插件不再以它为主场，见 §1.4。
2. **研究**：作为**上下文编排的可测量实验台**——「上下文对模型表现的影响」这一命题的受控实验载体。→ **本插件的主场**：包含「**迭代预设**」（效果的读数端）与「**研究上下文内容对模型表现的影响**」（「最优上下文」命题的度量装置），见 §1.4。

### 1.2 反定位（不是什么）
- **不是**从零写的 agent 运行时：会话、模型路由、重试、压缩、工具、权限、Web GUI **一律复用 DSH 原生**。
- **不是** SillyTavern 的移植或兼容层：**导出/导入 ST 卡格式**是互操作需求，不是架构目标。
- **不是**通用聊天前端：没有卡与装配规则就没有本能力。
- **不是**评测框架本身：它**产出证据**，评分与统计归独立的测量装置（见 §5.4）。

### 1.3 与上游的关系（自持边界）
| 层面 | 可以做 | 不可以做 |
|---|---|---|
| 文件格式（ST 卡 PNG/JSON、世界书 JSON） | 读、写、往返 | — |
| **行为/接口**（候选与正文分离、后台结算、按需读上下文） | 借鉴并自己实现 | — |
| **源码** | 只读用于判断「有没有这条路」 | **不复制任何代码片段** |
| 分发 | 自己的仓库、自己的许可 | 不把上游代码并进自研仓库 |

### 1.4 功能分区（与 `dsh-profile-tavern` 的分工）· 2026-09-22 主人定调

> **主人的判据（原话）**：「最好还是要完善一下功能分区……**两个类似物一定要有不同的功能优势，不然就合并**」。
> 这是一条**判据**不是形容词：拿不出差异化优势的那一方（或那一块功能）就该被合并掉。**下面先拿它查本插件自己。**
>
> **主人的分区（原话 · 同日后续）**：「**那他那边就主要满足我的游玩需求，那本地的功能是用来迭代预设，还有就是研究上下文内容对模型表现的影响**」。

**总分区：§1.1 的两个并列目的，在这里分家。**

| §1.1 的目的 | 归谁 | 判据 |
|---|---|---|
| **娱乐**（导卡、自由游玩、沿剧本推进） | `dsh-profile-tavern`（他那边） | 主人的主观体验 |
| **研究**（上下文编排的可测量实验台） | **本插件** | 可复现的读数 |

**本插件的两条职责（主人指定）**：

1. **迭代预设** —— 但**不是**预设文件的编辑器，而是**改动效果的读数端**：改一版 ⇒ 装配 ⇒ 跑真模型轮 ⇒ 出**可比**的读数。
2. **研究上下文内容对模型表现的影响** —— 即 **2026-09-21「最优上下文」命题**在本侧的落地。那条命题的结论直接规定了本插件该长什么样：
   - 命题单独成立**太便宜**（「最好」的定义域就是全体上下文，上确界必存在）⇒ 必须补三个限定：**上下文空间怎么定义**（哪些旋钮可拨）/ **「最好」用什么可测判据** / **搜索预算**。
   - **存在的是「区域」不是「点」**（无梯度、离散、会跳变；实测反例：给某预设块加约束，占比 30.0% → 30.6%，方向反了）⇒ 目标是**平台区**，不是尖峰——**尖峰在模型版本变动时会塌**。
   - **可搜索性只能靠「先验 + 度量」** ⇒ 工程等价物是「**一个可度量的搜索循环**」，本插件就是那个循环的**执行与度量装置**。
   - **最优随模型漂移** ⇒ 任何上下文资产**必须配回归夹具**，否则模型升级即静默失效。

**三方边界（预设这条线上谁干什么）**：

| 层 | 归属 | 产出 | 面 |
|---|---|---|---|
| 流程规范（五态状态机 / 逐态判据 / 改动铁律 / 静默失败清单） | 技能 `tavern-preset-iteration`（**正本**） | 规范 | — |
| 预设**文件**的工程（`preset_status`/`gate`/`diff`/`metrics`/`release`） | 插件 `dsh-preset-ops` | 文件与闸门 | **静态** |
| 预设**效果**的实验（装配 → 真模型轮 → 逐轮读数） | **本插件** | 证据 | **动态** |

⇒ 三方**不重叠**：改文件是 `dsh-preset-ops` 的事；判「改得好不好」必须跑模型，而**跑模型并出可复现证据**这一块**目前无人承担**——那就是本插件的职能。**本插件不新增预设编辑能力**（撞上规则 4 就该被合并）。

**分区规则（碰到一个功能，按序判它归谁）**：

1. **价值在「人玩得爽」→ 归他那边**：候选、后台结算、场景图像、剧本/时间线/MVU 转换、世界书 BM25、历史导入救援、品牌化 UI。这些要么吃 ST 生态资产，要么只在主观体验上成立。
2. **价值在「能被判据检验 / 被 agent 程序化驱动」→ 归本插件**：装配单逐字节重建、原子回退字节级、ST 卡往返**不改卡**、无旁路（行为级）、成本与缓存读数。
3. **两边都要 ⇒ 只走 `数据面` 互通，绝不走 `代码依赖`**：ST 卡 PNG/JSON 与世界书 JSON 是**开放格式**，双方各读同一份文件即可互通；但**不链接对方模块**——对方是 AGPL-3.0 且内联了 ST 资产，链接会**污染本插件的自持优势**（§1.3）。
4. **两边都要、而本插件拿不出差异化优势 ⇒ 本插件收敛**（见下表）。

**自审（按主人的规则查自己，不合格的应被合并掉）**：

| 本插件的一块 | 差异化优势 | 裁决 |
|---|---|---|
| 装配器 / 装配单 / 回退 | **他那边完全没有判据面**（214 模块零测试） | ✅ 主场，继续加深 |
| 世界书触发匹配 | ⚠ **没有**——他有 `worldbook-bm25` / `worldbook-recall` / `worldbook-filter-context` 一整套，本插件只有「纯函数可测」一点 | ⚠ **收敛为契约层**：保留可测的匹配语义 + 读同一份 JSON，**不追功能厚度** |
| 卡读写 | ⚠ 功能重叠；优势仅「往返不改卡」这一条判据 | ⚠ 同样**收敛为契约层** |
| 预设管理 | ❌ 无——正本已在 `tavern/色欲之罪预设/` + 技能 `tavern-preset-iteration` + 插件 `dsh-preset-ops`（§7） | ❌ **只读，不重造** |

**结论：不合并，而且分工是「目的级」的。** 差异化优势两侧都可核实（他：214 模块广度 + ST 生态；我：判据面 + 自持许可）——但真正的分界不是能力，是**目的**：**「玩」归他，「量」归我**。
⇒ 本插件**不再向外扩功能**，只向那两条被指定的职责长：**迭代预设**（做效果的读数端）+ **研究上下文对模型表现的影响**（做那个可度量搜索循环的执行与度量装置）。三件具体的待补（对应 §9 与 9-21 命题留下的口子）：① **上下文控制面表**（哪些旋钮可拨 —— 命题的三限定之一，尚未形式化）；② **表现的可测判据**；③ **搜索预算与回归夹具**（模型漂移时资产不静默失效）。

## 2. 术语

- **卡（card）**：人物设定 + 开场 + 对话样例 + 正则 + 展示模板。
- **世界书（lorebook）**：按关键词/位置触发的条目集合。
- **预设（preset）**：上下文装配规则（槽位、顺序、触发、后处理）。
- **剧本（script）**：主线推进用的分段原文与进度锚点。
- **游玩会话（play session）**：一次游戏，含正文历史 + 后台状态。
- **装配单（assembly manifest）**：一次请求的**结构化描述**——每个片段来自哪个槽位、什么触发条件命中、注入在哪个深度、逐字节内容与哈希。**本能力的核心产物。**
- **后台结算（settlement）**：只改状态、不产生正文的独立 Agent 调用。
- **候选（candidate）**：与正文分开生成的若干行动选项。

## 3. 概念模型与不变量

### 3.1 三个 Agent，职责互斥
| Agent | 产出 | 写权限 |
|---|---|---|
| 正文 Agent | 叙事正文 | 只读状态 |
| 候选 Agent | N 个行动选项 | 只读状态 |
| 后台结算 Agent | 状态变更（结构化） | **唯一**状态写者 |

### 3.2 装配位置模型
槽位 = `system` / `persona_prefix` / `persona_suffix` / `before_history` / `depth-N`（倒插历史第 N 条之后）/ `after_history`；每条注入项带：来源、触发条件、优先级、是否可缓存。

### 3.3 不变量（违一则能力不成立）
1. **装配单即事实**：装配单逐字节重建出的请求体，必须等于实际发出的请求体。
2. **状态单写者**：只有后台结算 Agent 可改状态；正文与候选对状态只读。
3. **状态与正文同生共死**：回退必须原子——正文与状态一并还原到同一点。
4. **只追加**：已发出的历史前缀不得重写（缓存友好）；任何「重写历史」的设计须显式标注为破坏缓存。
5. **确定性**：同一输入 + 同一卡/预设/世界书 ⇒ 装配单哈希一致（模型采样除外）。

## 4. 契约（含调用点清单）

> ⚠ 本条目要求**契约必须写调用点**（§5.20 规则 3：只说「谁做什么」会漏点）。

### 4.1 存储布局
```
<dataDir>/
  cards/<cardId>/{card.json, source.png?, assets/}
  lorebooks/<id>.json
  presets/<id>.json
  scripts/<id>.json
  sessions/<sessionId>/{history.jsonl, state.json, manifests/<turn>.json}
```

### 4.2 工具面（宿主侧，初步）
| 工具名 | 意图 | 调用点 |
|---|---|---|
| `tavern_card_list` / `_read` / `_write` | 卡库读写 | 卡管理 UI、游玩会话启动、卡编辑 Agent |
| `tavern_lorebook_match` | 世界书触发匹配（纯函数） | 装配器（**唯一**调用点）、单测 |
| `tavern_assemble` | 产出装配单 | 正文/候选/后台三条路径**共用** |
| `tavern_state_apply` | 应用状态变更 | **仅**后台结算 Agent |
| `tavern_rollback` | 原子回退 | 游玩 UI、命令 |

### 4.3 装配器契约
`assemble(card, lorebook, preset, script, history, state, turnInput) -> { manifest, messages }`
- 纯函数、无 IO（IO 由调用方先取好喂入）⇒ **可离线单测**。
- `manifest` 含：`entries[]`（slot, source, triggerHit, depth, bytes, sha256）、`totalChars`、`hash`。

### 4.4 已识别的调用点风险（来自 §5.20 的事故史）
- 装配路径有**三条**（正文/候选/后台）⇒ 必须**共用** `tavern_assemble`；历史上「面板 3 种接入只改 1 种」「守护 3 条拉起路径只改 1 条」都出在这里。

### 4.5 上下文控制面（「哪些旋钮可拨」）· 2026-09-22 新增

> 这是 2026-09-21「最优上下文」命题三个限定中的**第一个**（另两个：可测判据 / 搜索预算）。
> **机器可读正本**：`src/control-surface.ts`（**数据不是机制**——它不改装配行为，只把既有行为里的可拨项说清楚）；
> **判据**：`tests/control-surface.test.mjs`。

九个旋钮，每个都写了「当前值 / 可拨范围 / 怎么量它的效果 / 装配单落点」：

| 旋钮 | 面 | 一句话（都是实现读出来的，不是照文档措辞抄的） |
|---|---|---|
| `slot` | 位置 | 6 类；**前 4 类并入开头同一条 system 消息**（不是 4 条消息），`depth-N` 才插进历史内部 |
| `order` | 顺序 | priority **只在同 slot 内生效**，越不过槽位边界（跨 slot 由 `SLOT_RANK` 定） |
| `trigger` | 触发 | `constant` 必中；否则子串匹配。⚠ **keywords 为空且非 constant ⇒ 永不触发，且不报错**（静默陷阱） |
| `probability` | 概率 | 同轮必同结果、跨轮会变。⚠ **装配单看不出**（见下「观测缺口」） |
| `budget` | 预算 | 超预算**只裁 lorebook 来源的 system 片段**；depth-N / after_history / 历史**都不参与裁剪** |
| `card-tier` | 卡片分级 | 卡片字段的优先级**写死在代码里** ⇒ ⚠ **不可拨**（控制面的硬边界，如实标注） |
| `template` | 占位符 | 7 个可用键；**未匹配的占位符原样保留**。⚠ 装配单不存模板 ⇒ 观测缺口 |
| `history` | 内容 | 只追加、不重写（不变量 4） |
| `state` | 内容 | 自由 JSON（§9.4）⇒ 可拨，但**不可校验** |

**判据（三条，全部可跑）**：① 每旋钮三列齐全（防占位）；② **每个旋钮必须指认装配单落点且路径能在真装配单上解出**——指认不出即空谈；③ **观测缺口必须自曝且不得被悄悄扩大**（只允许 `probability` 与 `template` 两个，新增须先在测试里登记——防「解不出就标 null」这个逃生通道被滥用）。

**两个观测缺口是诚实标注，不是遗漏**：`probability` 与 `template` 的作用在**单份装配单里看不出来**（前者只记录「中了」不记录「没中」；后者只存渲染后文本、不存模板）。要量它们必须做**多轮对照**或**同时持有模板**——这正是「可度量的搜索循环」下一步要补的东西。

**由本表带出的一处实现修复**：`parts[].source` 原先**不是身份**——`card:persona` 与 `card:scenario` 共用裸 `'card'`（而同族的 preset 用 `preset:<blockId>`、lorebook 用 `lorebook:<id>`），于是两段**不同**字段看起来像「同一来源注入两遍」。已统一为细粒度（`card:persona` / `card:scenario`）。**这是质量判据第一次跑就抓出来的**——判据有分辨力的实证。

## 5. 边界与信任

1. **卡与世界书是不可信输入**（第三方卡含 HTML/正则/脚本）⇒ 展示层隔离；正则与模板**不得**取得工具权限。
2. **卡内脚本不执行**：只做声明式解析；需要执行的一律走宿主已审核的扩展点。
3. **研究数据的边界**：装配单与请求往返属**我方的**取证数据；第三方案例内容按来源标注，不外发。
4. **测量装置独立**（自有许可，见 §1.3）：评分器、统计、报告**不并入本插件**，只读其产物格式。

## 6. 可证伪验收

> 跑法：`node scripts/acceptance.mjs`（一条命令出判据表 + 真数据读数 + A7 旁路面）。
> 退出码：`0` 全量通过 ｜ `1` 判据失败 ｜ `2` 判据通过但真数据不可达（PASS 降级）｜ `3` **测试器未能启动（仪器问题）**。
>
> ⚠ **`3` 是 2026-09-22 实测补上的一档**：原先脚本用 `spawnSync(..., { shell: true })` 启动测试器，而 `process.execPath` 在 Windows 是 `C:\Program Files\nodejs\node.exe` —— **路径里的空格被 cmd.exe 拆开**，进程起不来；又因 `run.status ?? 1` 把 `null` 映射成 `1`，于是「**仪器起不来**」被误报成「**判据失败**」（假红灯）。
> 现在不借 shell（node 的 `--test` 自己展开 glob），并把 `run.error` 单独判。**对照样本**：`spawnSync('不存在的路径', {shell:false})` ⇒ `error.code=ENOENT`、`status=null` ⇒ 证明 `run.error` 是正确判据。
>
> ⚠ **「跳过」不等于「通过」**：未设 `DREAM_TAVERN_CARDS` / `DREAM_TAVERN_WORLDS` 时，涉及真实数据的 **5 条判据**（4 张卡 + 1 世界书）会整组跳过，而 `npm test` 仍退出 0。⇒ 那种情况下**只有验收总闸的 exit 2 说出了真相**；跳过条数由脚本**从测试源码数出来**（曾写死为 4，已腐化，故改为现算）。

### 6.1 质量判据族（Q1–Q3）· 验「装得**好**不好」· 2026-09-22 新增

> ⚠ **与 A1–A7 分族**，别混为一谈：
> · **A1–A7（正确性）**：我发出的东西，是不是我以为发出的那个？
> · **Q1–Q3（质量）**：我以为发出的那个，是不是个好上下文？
>
> 实现：`src/quality.ts`（纯函数、无 IO、**不引入模型调用**）；判据：`tests/quality.test.mjs`。
> **它刻意不判断「内容好不好」**——那是内容层（预设作者）的判断；它只判**结构上已知会坏事**的形态。

| # | 判据 | 来源（不是凭空设的） | 判法 |
|---|---|---|---|
| Q1 | `no-duplicate`：同一来源或同一文本不得被装进上下文两次 | 2026-09-22 世界书重复注入事故（单卡请求被撑到近 20k 字） | 按 `parts[].source` 与 `parts[].sha256` 分组，出现 >1 即红，并点名是哪些 id |
| Q2 | `norm-first`：输出规范必须落在 **system 区段最前** | 酒馆实战教训②：「格式漂移几乎全因规范太靠后」（`preset.ts` 头注） | 规范块须 `slot==='system'` **且** priority 不低於 system 区段最高者（两条都要，因为区内顺序由 priority 定） |
| Q3 | `within-budget`：不得超预算 | `overBudget` 字段的存在理由：须响亮记账、不静默截断 | 读 `manifest.overBudget` 与 `totalChars`、`dropped.length` |

**判据的判据（本族的自证）**：每条各配一个**尸体样本**，并要求它**只让自己红**（另两条保持绿）⇒ 三条互不掩盖、红点能精确定位；再加一个对照组证明「三条若全恒绿则本节是装饰」。
**跑法**：`npm test`（Q 族与 A 族同批）。**Q1 第一次跑就抓到一处真缺陷**（见 §4.5 末段：`parts[].source` 原先不是身份）。
